# 守宮客服 Agent 專案統整

**專案目標**：客人在網頁聊天小工具詢問「有沒有這種樣式/長怎樣」時，系統自動用
圖片辨識比對出實際商品，再用 LLM 組成自然的回覆——回覆的價格、庫存、樣式一律
根據資料庫真實資料，不能瞎掰。

**專案規模設定**（一開始釐清的需求）：
- 商品規模：中大型，幾百張以上、之後會持續增加 → 需要真正的向量搜尋，不是簡單比對
- 起始資料：完全從零開始
- 回覆的依據：不是「人工審核每則回覆」，而是「有庫存/價格表單，回覆要根據裡面
  可以搜尋到的資料」→ 走「資料庫查詢 grounding」的設計，不是人工審核流程
- 客服通路：自己網頁上的獨立聊天小工具（不是 LINE/FB 之類的第三方平台），
  首頁 `/` 打開來直接就是全螢幕聊天室，之後要嵌進別的網站再抽出嵌入版本

## 整體架構（5 個階段）

```
客人問題（文字/照片）
      │
      ▼
Phase 2：圖片向量搜尋 / 關鍵字搜尋 ──→ 查出「真的存在」的候選商品
      │                                  （來自 Phase 1 的商品資料庫）
      ▼
Phase 3：LLM 組回覆 ──→ 只能講候選商品裡的事實，查不到就老實說
      │
      ▼
Phase 4：網頁聊天小工具 ──→ 把上面串起來，變成客人看得到的介面
      │
      ▼
Phase 5：紀錄 + 低信心覆核佇列 ──→ 事後可以回頭看系統講了什麼、哪些不確定
```

技術棧：Python + FastAPI（後端）、SQLite + SQLAlchemy（商品資料庫，本機開發用；
部署後計畫換成 Railway 自帶的 Postgres）、Chroma（向量資料庫）、Claude API（LLM 回覆）。
照片檔案部署後計畫存到 Cloudflare R2。部署平台是 Railway（跟你的 Kaso 專案同一種方式）。

## 各階段進度

### ✅ Phase 1：商品目錄資料庫 + 後台表單（已完成、已驗證）

- `models.py`：`Product`（物種、樣式、價格、庫存、描述、上下架狀態、**精選旗標**）、
  `Photo`（照片檔案、是否已算過影像特徵）
- `main.py`：FastAPI 後端，新增/列表/查詢/更新商品、上傳照片
- `static/admin.html`：後台表單網頁，新增商品、改價格庫存、上下架、**勾選精選**
- `validate_phase1.py`：端對端驗證，全部通過。**這支腳本現在會先把
  `DATABASE_URL`/`GECKO_SHOP_UPLOAD_DIR`/`GECKO_SHOP_CHROMA_PATH` 環境變數指到獨立的
  測試專用路徑，才 import 專案程式**——舊版曾經因為直接刪掉/重建 `gecko_shop.db`，
  不小心洗掉過一次正式資料（詳見下方「發生過的事故」），現在已經修好、不會再發生。

### ✅ Phase 2：影像特徵 + 向量搜尋（已完成——過程中發現「已經在用真的 CLIP 了」）

- `embeddings.py`：把照片轉成特徵向量
- `vector_store.py`：Chroma 向量資料庫包裝（存向量、找最像的前 k 筆），路徑可用
  `GECKO_SHOP_CHROMA_PATH` 環境變數覆寫
- `backfill_embeddings.py`：把還沒算過特徵的照片補算一遍——**已改成透過
  `storage.py` 讀照片**（不管照片存在本機還是 R2 都能用），部署後也能正常跑。
- API：`POST /search/image`（上傳照片，回傳最像的前幾個商品 + 相似度）

**重要更正（原本文件寫錯了）**：舊版說法是「這個環境連不到 huggingface.co，
所以在用顏色直方圖頂著」——**這個說法已經過時**。準備部署時檢查發現
`embeddings.py` 實際上早就是 `embeddings_clip.py`（真正呼叫 CLIP 模型）的內容
了，Chroma 裡的向量也確認是 512 維（CLIP `clip-ViT-B-32` 的輸出維度，不是直方圖
法會有的維度）——這個環境其實連得到 huggingface.co，之前的限制說明沒有跟著更新。
所以「換上真的 CLIP」這件事其實已經完成，不用再做。

**測出來的實際情況**：CLIP 對「這是不是豹紋守宮、拍起來像不像同一個場景」抓得
準（自我比對 10/10 是 100%），但對花紋/顏色這種細節的區分沒有到非常精細——
拿「橘化」的照片查，前幾名偶爾會混進「雪花系」這種顏色不同的商品（相似度都在
70-96% 之間，物種/整體外觀相近，但不是我們最在意的「花紋細節」）。這不是「沒接
CLIP」的問題，是通用 CLIP 模型本來就不是為了「守宮花紋分類」訓練的，算是這個
方案的天花板，除非之後想做更精細的模型微調。

**沿用之前的決定**：拍照搜尋功能先不主動對客人開放（Phase 4 v1 是純文字版），
低於 70% 相似度的比對結果會被 Phase 5 標記為低信心、進覆核佇列。

### ✅ Phase 3：LLM 自動回覆（已完成、已用真的 Claude API 實測過）

- `catalog_search.py`：把客人的問題（照片或文字）轉成「資料庫裡真的存在」的
  候選商品清單。照片查詢用 Phase 2 的向量搜尋（只留相似度 ≥55% 的結果）；
  文字查詢用關鍵字比對物種/樣式/描述欄位。**新增 `find_highlight_candidates`**：
  關鍵字完全比對不到時（客人問「你們都賣什麼」，或問的東西剛好沒有），不再回傳
  空清單，改成推薦「精選」（後台手動勾選）+「新進」（最近 14 天上架，沒有就退而
  求其次列最近上架 3–5 筆）商品，且一律排除庫存 0 的。
- `llm_reply.py`：把候選商品清單交給 Claude，組成自然的客服回覆。System prompt
  硬性規定：只能講候選清單裡有的商品/價格/庫存，清單是空的就老實說沒查到，
  庫存是 0 就說缺貨，絕對不能自己編。`generate_reply` 現在多一個 `is_fallback`
  參數，是精選/新進推薦時會告訴 LLM「這不是精準比對，別講得像剛好符合客人要的」。
- API：`POST /chat`（`message` 文字 + `photo` 照片，兩個都可選）→ 回傳
  `{"reply": "...", "candidates": [...], "is_fallback": bool}`，`candidates`
  就是這次回覆實際依據的資料，之後做紀錄/覆核會用到。
- `validate_phase3.py`：驗證查詢/防呆邏輯（不需要 API key 也能跑）全部通過。
- **真的用 `ANTHROPIC_API_KEY` 實測過 `/chat`**：抓到商品時正確報價格/庫存、
  查不到時老實說沒有（不會亂編）、泛問時會自然介紹精選/新進商品，品質沒問題。

**已知限制（老實講）**：
- 文字搜尋還是關鍵字比對，不是真的語意理解（客人用詞跟資料庫欄位差太多會抓不到，
  但現在至少查不到時會退而求其次推薦精選/新進，不會讓客人得到「沒查到」的死結）。
- 物種欄位刻意不用模糊比對（因為店裡目前只賣豹紋守宮，"守宮"兩個字幾乎每筆
  商品都中，模糊比對反而會誤配到問其他物種的客人）。

### ✅ Phase 4：網頁聊天小工具（已完成、已在瀏覽器裡實測過）

- `static/index.html`：首頁 `/` 打開來就是的全螢幕聊天室（不是浮動按鈕），純問答
  （查價格/庫存/樣式）+「聯絡我們預訂」CTA 按鈕（先接 `curesname@gmail.com`），
  不做結帳/付款。v1 先不做拍照上傳（等 CLIP 換上去再加）。
- **支援多輪對話**：前端（客人瀏覽器）用一個 JS 陣列保留這個分頁最近的對話文字
  （最多 20 則，純前端記憶體，重新整理就清空），每次呼叫 `/chat` 時把 `history`
  一起用 JSON 字串送過去；`main.py` 解析後轉交給 `llm_reply.generate_reply`，
  組成 Claude 的多輪 `messages`，讓 LLM 聽得懂「這隻」「高彩那隻」這種接續問法。
  不同客人的瀏覽器各自獨立，不會共用到彼此的對話。
- 已實測：問「有沒有橘化的」→ 接著問「高彩那隻還有貨嗎」，LLM 正確接住上下文，
  講出正確的庫存/價格，不是重新問一次的空白狀態。
- 之後要嵌進別的網站，再把 `static/index.html` 這套介面抽出來做成嵌入版本。

### ✅ 額外功能：後台批量上傳照片 + AI 批量標籤 + 彈窗人工檢查

`static/admin.html` 現在是**分頁式**後台：「批量新增」＋「商品清單」（原本單筆
新增表單已經拿掉，整個新增流程改用批量版）。

- `photo_tagging.py`：`suggest_tags(image_bytes, media_type)` 把單張照片丟給
  Claude（多模態視覺輸入），依外觀猜物種/樣式/描述，回傳 JSON，附一句
  `confidence_note` 老實講這個判斷有多不確定。species 欄位規定只能是純中文物種
  俗名（跟既有資料格式一致），樣式欄位維持「中文 (English)」格式。
- API：
  - `POST /products/suggest_tags`：單張照片版本。
  - `POST /products/suggest_tags_batch`：**批量版**，一次丟多張照片，逐張呼叫
    Claude，回傳順序跟上傳順序一致；單張猜失敗不會讓整批中斷，那張的 `error`
    欄位會帶錯誤訊息，其他張照樣正常。
- 「批量新增」分頁流程：設定批次預設價格/庫存 → 選多張照片 →「AI 批量標籤」→
  跳出**彈出視窗**，裡面是一張表格列出每張照片的縮圖 + AI 建議的物種/樣式/描述
  （都可編輯）+ 價格/庫存（預先填好批次預設值，可個別調整）+ 精選勾選 → **每一
  列有自己的「確認新增」按鈕，按下去立刻呼叫 `POST /products` 存那一筆**（不是
  全部填完才一次送出），存好會標記「✅ 已新增」並鎖定那一列；也有「全部確認新增」
  可以一次跑完所有還沒確認的列。
- **防呆**：確認新增時如果價格或庫存是 0，會先跳出瀏覽器原生確認視窗
  （"這筆的價格/庫存是 0，確定要這樣新增嗎？"）要你二次確認，不會悄悄存進一筆
  庫存或價格是 0 的商品。
- 已完整實測過：批量標籤兩張真實照片、彈窗渲染正確、單列確認新增成功寫入
  資料庫（含照片正確存檔+算好影像特徵）、價格 0 會觸發二次確認擋下。

### ✅ Phase 5：紀錄 + 低信心覆核佇列（已完成、已實測）

- `models.py`：新增 `ChatLog` 資料表（每通 `/chat` 都存一筆：客人訊息、回覆、
  candidates JSON、is_fallback、是否低信心、低信心原因、是否有照片、照片路徑/
  保留期限、是否已覆核）。這是全新的表，`Base.metadata.create_all` 會自動建立，
  不用額外遷移。
- **低信心判定邏輯**（寫在 `main.py` 的 `/chat` 裡）：
  - 照片查詢：完全查不到候選商品，或最像的那筆相似度 < 70%
    （`catalog_search.LOW_CONFIDENCE_IMAGE_SIMILARITY`，介於「有查到」的 55% 門檻
    之上但不算有把握）。
  - 文字查詢：關鍵字完全比對不到、觸發了 fallback 推薦。
- **只有低信心的對話**才會把客人上傳的原始照片存進 `static/chat_log_photos/`
  （獨立於商品照片的資料夾），並記錄 90 天後的保留期限；一般對話只留文字，不留照片。
- `cleanup_chat_logs.py`：清掉到期的照片檔案（保留文字紀錄，只清照片）。**部署後
  記得排程定期跑**（例如每天一次），本機開發階段先手動跑。
- API：`GET /chat_logs`（覆核佇列，預設只回傳低信心+還沒看過的）、
  `PATCH /chat_logs/{id}`（標記已看過）。
- `static/admin.html` 新增第三個分頁「低信心覆核」：卡片式列表，顯示照片縮圖
  （沒留底的話顯示「無留底」或「純文字」）、低信心原因、客人訊息、系統回覆、
  時間，按「標記已看過」會讓佇列變短；分頁標題會顯示未處理筆數的紅色數字徽章。
- 已實測：文字 fallback、圖片相似度不足這兩種低信心情境都正確寫入 `ChatLog`、
  正確在覆核佇列裡顯示、標記已看過後正確從佇列消失、照片留底+90天期限正確設定、
  `cleanup_chat_logs.py` 執行正常。
